# 需求分析

## 业务背景与机会

### 现状问题

在企业级数据中心（如教育、医疗）场景，运维人员常需定位复杂 OS 故障（僵尸进程、磁盘 I/O 异常、配置漂移）。传统方式依赖脚本与经验，排障效率与一致性不足。

### 业务机会

利用大模型的文本理解能力与 MCP 工具协作能力，将“人工排查”升级为“对话式诊断 + 受控执行 + 可追溯审计”，显著降低上手门槛并提升排障闭环效率。

---

## 产品愿景与阶段目标

### 产品愿景

通过大模型 + MCP 构建可治理、可审计的运维智能体：
- 让运维人员以自然语言完成环境感知、故障排查与操作执行。
- 通过安全护栏、最小权限、风险确认机制，避免高危误操作。

### 项目目标

- 构建一组通过 Docker 运行的、支持 loongarch64 架构的功能完备的运维 agent微服务平台
- 支持B/S架构,能够对话式诊断 + 工具授权执行 + 可追溯审计
- 保证后端提供完整的 OpenAPI 风格接口与数据契约（见 `doc/api-spec/`），以支持前端或第三方系统对接。

### 非目标

- 非 Linux 平台适配。
- 多租户用户体系与统一身份认证。
- 通用任意命令执行代理。
- 全量实时监控平台能力。

---

## 用户角色

- 运维人员：通过自然语言发起诊断和操作请求，审核高风险动作，查看审计日志追溯行为。

---

## 功能需求

- 制定目标后可以独立自主的完成任务
- 支持 Thought->Action->Observation 循环迭代
- 支持基于 LLM 完成 plan 模式：根因分析、任务编排、方案推荐
- 支持多智能体分工协作（预留 LangGraph sub-graph 扩展点，当前版本不实现）
- 支持问题解决后把解决方案更新到知识库

### 工具层

需求：
- 基于MCP实现运维工具/技能的标准化封装与注册
- 解耦底层工具依赖，支持运维能力灵活扩展 

### 感知层

需求：
- 采集系统当前状态（常用服务器性能指标，网络，日志，系统配置）
- 对非结构化数据进行结构化转换
- 扩展预留：OpenTelemetry 数据源对接（非当前阶段验收）

### 安全控制层

#### 最小权限执行

需求：
- 遵循RBAC最小权限原则
- tool-server 作为 Docker 容器运行，通过挂载权限与 Linux capabilities 实现最小权限约束；执行前通过审批、备份确保操作可回退
- 能够获取工具层所拥有的执行权限

#### 安全护栏

需求：
- 对工具执行操作进行分级（只读 / 可回滚 / 破坏性），非只读操作须人工确认
- 三层安全护栏：web-server 规则匹配与审批、tool-server 二次校验、web-server 异常捕获
- 工具操作超时熔断
- 审批超时自动拒绝（默认 5 分钟）


### 日志层

需求：
- 应用日志：记录系统运行状态、错误和关键事件
- 追踪日志：完整记录 Agent 从感知环境、推理决策到操作执行的全链路（时间、主体、动作、结果、会话 ID）

## 非功能需求（NFR）

- 可靠性：严禁在未授权情况下修改系统关键配置。
- 安全性：依赖安全控制层三层护栏（规则匹配、审批、工具端二次校验）阻断恶意工具调用。
- 可维护性：模块边界清晰，关键路径可测试。
- 可扩展性：新增 MCP Server/工具不改核心会话主循环。
- 可观测性：关键流程必须具备结构化日志和错误分层。

---

## 业务规则与约束

- 任何工具执行必须先经过权限上下文判断。
- MCP 配置必须通过策略过滤后进入连接队列。
- 禁止无限重试。
- 所有会话和工具调用操作必须全程可追溯。
