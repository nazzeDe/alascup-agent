# 麒麟安全智能运维 Agent 软件功能演示 PPT 大纲

> 用途：作为中国软件杯比赛软件功能演示 PPT 的内容蓝本。
> 原则：允许适度强化表达，但所有能力必须能从当前项目文档、代码结构、测试设计或赛题要求中找到支撑。

## 1. 封面

标题：面向银河麒麟操作系统的安全智能运维 Agent 设计与实现

副标题：基于大模型 + MCP + 安全护栏的可审计 OS 运维智能体

建议展示：
- 项目名称：Alascup Agent
- 赛题方向：中国软件杯 / 麒麟操作系统 / 智能运维 Agent
- 关键词：自然语言运维、MCP 工具编排、安全审批、最小权限、全链路审计

演讲重点：
- 一句话定位：把传统“脚本 + 人工经验”的 Linux 运维过程，升级为“对话式诊断 + 受控执行 + 可追溯审计”的智能运维平台。

## 2. 赛题背景与核心挑战

标题：从人工排障到可信智能运维

内容要点：
- 企业级 Linux 节点常见问题复杂：僵尸进程、磁盘 I/O 异常、配置漂移、日志暴涨、服务异常重启。
- 传统运维依赖人工经验和脚本积累，排查链路长、操作风险高、过程难复盘。
- 大模型具备自然语言理解和推理能力，但直接赋予系统执行权限会带来不可控风险。
- 本项目聚焦赛题核心矛盾：既要让 Agent 能感知和执行，又要防止误删、误操作、提示词注入和越权调用。

建议图示：
- 左侧：传统运维流程，告警 -> 查命令 -> 写脚本 -> 人工判断 -> 执行。
- 右侧：智能运维流程，自然语言目标 -> Agent 诊断 -> 安全校验 -> 审批执行 -> 审计回放。

## 3. 赛题要求与项目响应

标题：围绕五大能力构建完整闭环

建议做成对照表：

| 赛题要求 | 项目实现 |
| --- | --- |
| OS 环境深度感知 | CPU、内存、磁盘、网络、进程、日志、systemd 状态等 MCP 工具 |
| MCP 运维插件化 | tool-server 基于 fastmcp 暴露工具，web-server 作为 MCP Client 动态发现和调用 |
| 安全意图校验器 | web-server 规则引擎 + tool-server 伴生分类工具 + bash AST 只读分类 |
| 最小权限代理执行 | tool-server 容器化运行，使用挂载范围和 Linux capabilities 控制执行边界 |
| 推理链路溯源 | PostgreSQL 保存会话、消息、工具调用、审计事件、LLM trace |

强调句：
- 我们不是做一个“能执行命令的聊天机器人”，而是做一个可治理、可审批、可追溯的 OS 运维 Agent。

## 4. 产品定位与演示目标

标题：面向麒麟服务器节点的 B/S 智能运维平台

内容要点：
- 采用 B/S 架构，用户通过浏览器进入聊天式运维界面。
- 支持自然语言输入运维目标，由 Agent 自动完成信息收集、分析判断和工具调用。
- 对只读诊断自动执行，对高风险动作触发内联审批。
- 所有关键行为落库，支持会话回看、工具结果追踪和审计复盘。
- 目标运行环境面向 LoongArch 架构 + 麒麟高级服务器版 V11。

建议截图：
- 前端聊天页面。
- 工具调用内联展示。
- 审批卡片。
- 会话列表或历史回看。

## 5. 总体架构

标题：感知 - 决策 - 护栏三层协同

架构分层：
- 前端展示层：Vue 3 + Bootstrap 5 + Nginx，负责聊天、流式展示、工具结果和审批交互。
- 智能编排层：FastAPI + AgentLoop + SSE，负责 ReAct 循环、上下文管理、工具审查、会话持久化。
- MCP 工具层：fastmcp tool-server，封装 OS 感知工具和运维操作工具。
- 数据审计层：PostgreSQL 保存 chat_sessions、messages、tool_calls、audit_events、llm_traces。
- 模型接入层：OpenAI 兼容 API，支持可配置主模型与摘要模型。

建议图示：
用户浏览器 -> frontend/nginx -> web-server/AgentLoop -> MCP tool-server -> 麒麟 OS 资源
旁路连接 PostgreSQL、LLM API、安全规则配置。

## 6. 核心链路：Thought - Action - Observation

标题：让 Agent 像运维专家一样迭代排查

内容要点：
- Thought：理解用户目标，形成排查计划。
- Action：调用 MCP 工具收集系统状态或申请执行操作。
- Observation：读取工具结果，继续判断根因。
- 循环退出：LLM 判断任务完成、达到轮次上限、用户拒绝审批或触发安全熔断。
- 静态只读工具可并行预执行，提升诊断响应速度。

建议演示脚本：
用户输入：“服务器响应变慢，请排查是否有 CPU 或内存异常。”

预期展示：
- Agent 输出推理过程。
- 自动调用 get_cpu_info、get_memory_info、get_process_list。
- 汇总高占用进程和风险判断。

## 7. OS 深度感知能力

标题：从系统指标到运维上下文的多维感知

内容要点：
- 性能指标：CPU、内存、磁盘、网络。
- 进程视角：进程列表、资源占用、异常进程识别。
- 日志视角：系统日志、应用日志、journalctl 查询。
- 服务视角：systemd 服务状态和重启能力。
- 扩展感知：预留 eBPF 探针能力，包含 tcpdrop、oomkill、biolatency、execsnoop、syscount 等探针脚本。

建议表达：
- 项目不仅采集“单点指标”，而是为 Agent 提供可组合的运维上下文，使模型能围绕问题动态选择证据。

注意边界：
- eBPF 可表述为“已预置探针脚本与测试适配”，不要说成已经完成生产级全量监控平台。

## 8. MCP 插件化工具体系

标题：把 OS 运维能力标准化为 Agent 可调用工具

内容要点：
- tool-server 基于 fastmcp 暴露 MCP 工具，web-server 动态发现并注册。
- 工具统一带有元数据：is_read_only、is_rollbackable、mutable、hidden。
- 可变工具通过伴生分类工具实现运行时风险判断，例如 bash -> bash_classify。
- 新增工具无需改动核心 Agent 主循环，增强系统扩展性。

建议图示：
MCP Tool Registry：
- get_cpu_info
- get_memory_info
- get_disk_usage
- get_network_info
- get_process_list
- read_logs
- bash / bash_classify
- systemd status / restart

强调句：
- 工具插件化让 Agent 的能力边界清晰可控，也方便面向不同麒麟节点扩展专用运维技能。

## 9. 安全护栏设计

标题：三层安全护栏，解决 AI 推理不可控

三层结构：
- 第一层：web-server 审查层，统一拦截所有 tool_call，执行规则匹配、审批流转和审计记录。
- 第二层：tool-server 二次校验，执行前校验 approval_status 和 request_id，拒绝未授权调用。
- 第三层：错误恢复与熔断，限制最大迭代轮次、Token 上限、工具超时和审批超时。

风险分级：
- 只读：自动执行，如 CPU、内存、日志查询。
- 可回滚或需确认：进入审批。
- 高危或黑名单：拒绝执行并记录审计。

建议演示：
- 输入“清理磁盘空间”。
- Agent 先只读分析磁盘占用。
- 当涉及删除或清理时弹出审批卡片。
- 用户拒绝后，Agent 给出替代建议；用户批准后，工具执行并记录结果。

## 10. bash 安全分类与抗误操作能力

标题：对命令行执行面进行细粒度收敛

内容要点：
- bash 是最灵活也最危险的运维入口，因此项目将 bash 设计为可变工具。
- 使用 tree-sitter-bash 解析 AST，解析失败或复杂结构 fail-closed。
- 只读命令白名单允许：ps、free、dmesg、journalctl、ss、ip addr、git status 等。
- 高危模式进入审批或拒绝：rm、kill、sed -i、重定向写入、curl/wget/ssh/nc、bash -c、eval、敏感文件读取。
- 对 /etc/shadow、~/.ssh/*、/proc/*/environ 等敏感路径执行 fail-closed。

建议做成对比：

| 命令 | 分类 | 行为 |
| --- | --- | --- |
| ps aux \| grep nginx | 只读 | 自动执行 |
| journalctl -u nginx --no-pager | 只读 | 自动执行 |
| rm -rf /var/log/app.log | 高风险 | 需要审批 |
| cat /etc/shadow | 敏感读取 | 拒绝或进入高危路径 |
| bash -c '...' | 复杂执行面 | fail-closed |

## 11. 人工审批与最小权限执行

标题：让关键操作“可控地自动化”

内容要点：
- 非只读操作不会直接执行，而是生成 ToolRequest。
- 前端在聊天流中展示审批卡片，包含工具名、参数、原因和备注。
- 审批支持 Approve / Reject，默认 5 分钟超时自动拒绝。
- tool-server 独立进程和容器边界隔离，不由 web-server 直接操作宿主机。
- 高风险工具执行必须携带 APPROVED 状态和合法 request_id。

建议强调：
- 该机制适合比赛场景中的“清理系统垃圾”：Agent 可以发现大日志文件，但删除前必须说明理由并等待授权。

## 12. 全链路审计与可追溯

标题：从用户指令到执行结果全程留痕

内容要点：
- messages 保存用户消息、Agent 回复、reasoning_content、tool_result。
- tool_calls 保存每次工具调用的参数、审批状态、执行状态、结果和错误。
- audit_events 仅追加写入，记录 actor、event、decision、transition、tool_name、params。
- llm_traces 记录模型、token、延迟、prompt 和 completion。
- 会话支持软删除，普通列表隐藏但底层审计仍可追溯。

建议图示：
接收指令 -> 感知环境 -> 推理决策 -> 安全校验 -> 审批决策 -> 执行结果 -> 审计事件。

强调句：
- 对比赛评委而言，系统不仅能完成任务，还能解释“为什么这样做、谁批准了、执行结果是什么”。

## 13. 前端交互与演示体验

标题：面向运维人员的低门槛对话式工作台

内容要点：
- 左侧会话列表按 Today、Yesterday、Previous 7 days 等分组。
- 中间聊天区统一展示用户消息、推理过程、工具调用、工具结果、审批卡片和错误提示。
- SSE 流式响应保证 Agent 思考、工具调用、审批等待都在同一条会话流中展示。
- 工具条目显示读写标记 R/W、运行状态、执行耗时和关键参数。
- Markdown 安全渲染使用 marked + DOMPurify。

建议截图：
- “只读诊断”工具调用成功。
- “高风险审批”卡片。
- “会话历史回看”页面。

## 14. 麒麟与 LoongArch 适配方案

标题：面向国产软硬件环境的部署设计

内容要点：
- 目标部署环境：自主指令系统 LoongArch + 麒麟高级服务器版 V11。
- 项目采用 Docker Compose 微服务部署，降低环境差异带来的安装复杂度。
- frontend、web-server、tool-server、PostgreSQL 通过内部网络通信。
- tool-server 端口仅容器内部访问，不直接暴露宿主机。
- 配置文件集中管理：servers.json、rules.json、llm.json。
- 日志挂载到宿主机 ./logs/，审计数据写入 PostgreSQL。

可加入麒麟 V11 背景：
- Linux 6.6 内核。
- KySEC、SELinux、KSAF 等安全能力为后续更深层的策略联动提供基础。

注意边界：
- 当前项目主要完成应用层 Agent、容器化隔离和工具安全控制；不要宣称已经深度集成 KySEC/KSAF 内核策略。

## 15. 典型演示一：系统资源健康诊断

标题：自然语言完成 CPU / 内存 / 磁盘 / 网络排查

演示输入：
“查看当前系统 CPU、内存、磁盘和网络状态，指出最值得关注的异常。”

演示流程：
1. 前端创建新会话。
2. Agent 进入 reasoning，形成检查计划。
3. 自动调用多个只读工具。
4. 工具结果通过 SSE 流式展示。
5. Agent 汇总异常点，给出进一步排查建议。

展示价值：
- 覆盖 OS 感知能力。
- 展示 MCP 工具调用。
- 展示只读工具免审批执行。
- 展示自然语言解释能力。

## 16. 典型演示二：磁盘清理的安全闭环

标题：清理不是直接删除，而是诊断、评估、审批、执行

演示输入：
“磁盘空间快满了，请分析哪些目录占用较多，并给出安全清理建议。”

演示流程：
1. Agent 调用磁盘和日志相关只读工具。
2. 输出可疑目录或大日志文件。
3. 生成清理计划，说明风险和影响。
4. 涉及删除或清理时，前端弹出审批卡片。
5. 用户批准后执行；拒绝后 Agent 停止高危动作并给出替代方案。

展示价值：
- 对应赛题“清理系统垃圾”的典型场景。
- 展示安全护栏、审批和审计。
- 体现 Agent 不是盲目执行命令，而是先收集证据再行动。

## 17. 典型演示三：服务异常与日志分析

标题：从服务状态到日志证据的根因分析

演示输入：
“检查 nginx 服务状态和最近 30 分钟日志，判断是否有异常重启或错误。”

演示流程：
1. Agent 查询 systemd 服务状态。
2. 读取限定时间范围的 journalctl 或日志。
3. 识别错误关键词、异常重启、端口占用或配置问题。
4. 如果建议 restart，必须进入审批。
5. 最终输出根因判断、影响范围和处理建议。

展示价值：
- 覆盖日志分析、服务状态、根因分析。
- 展示“先诊断后修复”的运维方法。

## 19. 创新点总结

标题：把“会调用工具的 Agent”升级为“可信运维智能体”

创新点：
- MCP 插件化工具总线：运维能力以标准工具形式接入，Agent 能力可扩展。
- ReAct + SSE 流式编排：推理、工具调用、审批和结果在同一会话中持续呈现。
- 双层工具安全判断：web-server 策略审查 + tool-server 伴生分类与执行前校验。
- bash AST fail-closed 分类：对最危险的通用命令入口进行结构化收敛。
- 审计不可变与 LLM trace：让智能决策过程可回看、可定位、可问责。
- 面向麒麟/LoongArch 的容器化部署：适配国产软硬件比赛环境。

## 20. 实用价值与应用前景

标题：可落地的安全智能运维底座

内容要点：
- 降低 Linux 运维门槛：自然语言描述目标即可启动排查。
- 提升排障效率：Agent 自动选择工具并汇总证据。
- 降低误操作风险：高风险动作默认审批，未授权不执行。
- 满足审计要求：适合教育、医疗、政企数据中心等合规要求较高场景。
- 可扩展方向：接入更多 MCP 工具、强化 eBPF 实时观测、结合麒麟安全策略、沉淀故障知识库。
