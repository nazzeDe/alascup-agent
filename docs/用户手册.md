# 软件产品说明书（Alascup Agent 用户手册）

> 软件版本：0.1.0
>
> 文档版本：1.0
>
> 更新日期：2026-07-17

## 1. 产品简介

Alascup Agent 是面向 Linux 数据中心运维场景的对话式智能运维平台。运维人员可以通过浏览器输入自然语言，让 Agent 协助完成系统状态查看、故障诊断、日志分析、进程与资源排查，以及在人工审批后执行受控运维操作。

系统采用 B/S 架构，由前端页面、web-server 编排服务、tool-server 工具执行服务和 PostgreSQL 数据库组成。日常用户主要通过前端聊天页面使用系统；管理员需要负责部署、模型配置、工具安全规则和日志审计。

当前版本提供 18 个业务 MCP 工具，覆盖基础系统指标、PostgreSQL、tool-server 运行状态、受控 Bash 和 8 类 eBPF 诊断。用户输入、工具调用和执行结果都有独立的安全检查与记录，不依赖模型自行遵守一段提示词。

### 1.1 适用场景

- 查看服务器 CPU、内存、磁盘、网络、进程等运行状态。
- 通过受控 `journalctl`、`systemctl status` 等命令分析 Linux 日志和服务状态。
- 定位僵尸进程、磁盘 I/O 异常、配置漂移、资源占用异常等问题。
- 在审批确认后执行清理、重启服务、命令行操作等高风险运维动作。
- 追溯某次诊断过程中 Agent 做出的决策、调用的工具和执行结果。

### 1.2 非适用场景

- 非 Linux 平台运维。
- 多租户账号体系、统一身份认证和权限管理。
- 全量实时监控、告警平台或指标大屏。
- 无人工确认的自动化高危变更。

### 1.3 用户角色

| 角色 | 主要职责 |
|------|----------|
| 运维人员 | 通过聊天页面发起诊断，查看工具结果，审批或拒绝高风险操作，回看历史会话。 |
| 系统管理员 | 部署系统，维护 LLM 配置、MCP Server 配置、安全规则、日志和数据库。 |
| 审计人员 | 根据会话、工具调用记录和审计日志追溯操作过程。 |

## 2. 核心概念

### 2.1 会话

一次连续的问题处理过程称为会话。会话中会保存用户消息、Agent 回复、推理过程、工具调用、审批记录和执行结果。新会话由用户首次发送消息时自动创建。

### 2.2 Agent 诊断循环

Agent 按照“思考、行动、观察”的方式处理问题：

1. 理解用户目标并形成排查思路。
2. 调用只读工具收集系统状态。
3. 根据工具结果继续分析。
4. 如需执行高风险操作，向用户发起审批。
5. 用户审批后执行工具，并根据结果给出结论。

### 2.3 工具调用

工具是 Agent 访问系统能力的方式，例如获取 CPU 信息、查看进程列表、采集 eBPF 事件或执行 Bash 命令。前端会以内联证据卡展示工具名称、读写标记、审批状态、执行状态和耗时。

点击证据卡可以展开查看 MCP Server、回滚属性、完整参数、结果预览和错误详情。结果超过 20 行或 16 KiB 时，页面只显示预览，但仍可复制完整结果。刷新页面后，已持久化的工具证据会随历史会话恢复。

工具读写标记含义：

| 标记 | 含义 |
|------|------|
| R | 只读工具，通常可自动执行。 |
| W | 写入或可变更工具，需要按安全策略审批或拒绝。 |

### 2.4 审批

当 Agent 需要执行非只读或高风险工具时，聊天流中会出现审批卡片。用户可以查看工具名称、审批原因、参数和可选备注，然后选择 Approve 或 Reject。

默认审批等待时间为 5 分钟。超时未处理时，系统自动拒绝该操作。

### 2.5 审计

系统会记录会话、消息、工具调用、审批决策、执行结果、Agent 状态变化和 LLM 调用追踪。审计日志写入 PostgreSQL，应用日志写入宿主机 `./logs/` 目录。

### 2.6 输入安全检查

用户消息在进入 LLM 前会经过独立规则检查。当前规则覆盖改写安全指令、索取 system prompt、索取凭据和绕过审批四类高置信提示词注入。

命中后，系统返回 `PROMPT_INJECTION_BLOCKED` 并结束本轮，不调用 LLM，也不进入工具执行。拒绝原因和规则 ID 会写入审计。该机制用于拦截已知模式，不能替代日常权限管理和审批检查。

### 2.7 诊断报告

当 Agent 已取得工具证据并完成故障诊断时，结论按六部分组织：根因结论、关键证据、置信度、备选原因、影响范围、处置建议与风险。普通问候和简单确认仍保持短回答。

## 3. 快速上手

### 3.1 访问系统

生产环境默认通过前端 Nginx 暴露服务：

```bash
http://localhost/
```

如果部署在远程服务器，请使用实际服务器地址或域名访问。

健康检查地址：

```bash
http://localhost/api/health
```

### 3.2 开始第一轮诊断

1. 打开浏览器访问前端页面。
2. 点击左侧 `+ New Session` 新建会话，或直接在空白聊天页输入问题。
3. 在输入框中描述排查目标，例如：

```text
查看当前系统 CPU 和内存占用，并分析是否存在异常进程。
```

4. 按 Enter 发送；如需换行，使用 Shift+Enter。
5. 等待 Agent 输出推理、工具调用和最终结论。

### 3.3 查看工具执行状态

聊天过程中会显示工具调用条目：

- `Running...`：工具正在执行。
- `Pending`：等待用户审批。
- `Done`：工具执行成功。
- `Failed`：工具执行失败，条目下方会显示错误信息。
- `Rejected`：工具被策略或用户拒绝，没有执行。

点击工具条目右侧箭头可展开证据。审批前建议先检查参数；执行后则重点核对结果、耗时和错误字段。

### 3.4 审批高风险操作

当出现 `Awaiting Approval` 审批卡片时：

1. 查看工具名称和参数，确认操作对象是否正确。
2. 阅读审批原因，判断是否符合当前处理目标。
3. 可在 `Message (optional)` 中填写备注。
4. 点击 `Approve` 批准执行，或点击 `Reject` 拒绝执行。
5. 审批后 Agent 会继续分析，并在聊天流中给出工具结果和结论。

## 4. 界面说明

### 4.1 左侧会话列表

左侧区域展示历史会话，并按时间分组：

- Today
- Yesterday
- Previous 7 days
- Previous 30 days
- Older

可执行操作：

| 操作 | 方法 |
|------|------|
| 新建会话 | 点击 `+ New Session`。 |
| 打开历史会话 | 点击会话条目。 |
| 删除会话 | 右键点击会话条目，选择 `删除`。 |

删除会话为软删除，普通会话列表不再显示该会话；底层审计记录仍可用于追溯。

### 4.2 聊天区域

聊天区域按时间顺序展示：

- 用户消息。
- Agent 推理摘要。
- Agent 回复。
- 工具调用。
- 工具执行结果。
- 审批卡片。
- 错误提示。

当系统正在生成或调用工具时，输入框旁的发送按钮会变为停止按钮。点击停止按钮可中断当前生成。飞行中的工具执行可能会自然结束，其结果仍可能被记录。

### 4.3 输入框

| 操作 | 快捷方式 |
|------|----------|
| 发送消息 | Enter |
| 输入换行 | Shift+Enter |
| 停止生成 | 点击红色停止按钮 |

建议一次输入一个明确目标。若目标复杂，可以先让 Agent 诊断并给出方案，再确认是否执行修复。

### 4.4 错误横幅

聊天区底部可能出现错误横幅：

| 标题 | 常见含义 | 处理建议 |
|------|----------|----------|
| Connection lost | 网络或 SSE 连接中断。 | 刷新页面或重新发送消息。 |
| Turn limit reached | 本轮 Agent 迭代次数达到上限。 | 重新发送更聚焦的问题，或让 Agent 继续上一结论。 |
| Context too large | 当前会话上下文过大，压缩后仍超限。 | 新建会话，并复制关键背景继续处理。 |
| Agent error | Agent 或服务端异常。 | 查看日志并联系管理员。 |
| Error | 输入命中安全规则或其他业务错误。 | 阅读错误原因；被安全门拦截时，不要换一种写法继续绕过。 |

## 5. 常用操作流程

### 5.1 查看系统概况

适用目标：快速了解当前系统资源状态。

示例输入：

```text
查看当前系统 CPU、内存、磁盘和网络状态，指出最值得关注的异常。
```

预期过程：

1. Agent 调用只读系统感知工具。
2. 前端展示多个 R 标记的工具调用。
3. Agent 汇总资源使用情况，并给出后续排查建议。

### 5.2 排查 CPU 占用过高

示例输入：

```text
服务器响应变慢，请帮我排查是否有 CPU 占用异常的进程。
```

建议关注：

- Agent 是否查看 CPU 负载、核心使用率和进程列表。
- 工具结果中是否有单个进程长期占用 CPU。
- Agent 是否区分短时峰值和持续异常。

如 Agent 建议终止进程，应先确认进程身份、业务影响和回滚方案，再审批相关操作。

### 5.3 分析内存异常

示例输入：

```text
检查当前内存使用情况，判断是否存在内存泄漏或 OOM 风险。
```

Agent 通常会查看内存、进程占用和系统日志。若需要进一步读取日志，可让 Agent 限定时间范围或关键词，避免获取全量日志。

### 5.4 排查磁盘空间不足

示例输入：

```text
磁盘空间快满了，请分析哪些目录占用较多，并给出安全清理建议。
```

推荐流程：

1. 先让 Agent 查看磁盘分区和目录占用。
2. 要求 Agent 先输出清理计划，不要直接删除。
3. 检查计划中的路径、文件类型和业务影响。
4. 对删除、移动、清理类操作逐项审批。

### 5.5 查看服务状态

示例输入：

```text
检查 nginx 服务状态和最近 30 分钟的相关日志，判断是否有异常重启或错误。
```

当前版本通过受控 Bash 调用 `systemctl status` 和 `journalctl` 等只读命令分析服务健康状况。命令会先经过 Bash AST 与参数分类；涉及 `systemctl restart`、配置修改或其他写操作时进入审批流程。

### 5.6 执行只读 bash 诊断命令

部分 bash 命令如果被分类为只读运维观测命令，可免审批执行。系统不会给 Bash 工具永久贴上“安全”标签，而是根据每次提交的完整命令重新判断；命令、子命令、flag、路径、重定向、命令替换和网络访问都会影响本次结果。

示例输入：

```text
执行只读检查：ps aux | grep nginx | head，帮我解释结果。
```

只读免审批通常覆盖：

- `ls`、`cat`、`sed -n` 等文件和日志读取。
- `ps`、`free`、`dmesg`、`journalctl` 等系统观测。
- `ss`、`ip addr`、`netstat` 等网络观测。
- `git status`、`git log`、`git diff --stat` 等 Git 诊断。

敏感读取、重定向、网络请求、shell wrapper、命令替换、可写 flag 等会进入审批或被拒绝。

### 5.7 执行高风险操作

示例输入：

```text
如果确认 nginx 状态异常，请先说明重启影响，然后请求我审批后再重启 nginx。
```

审批前建议检查：

- 工具名称是否符合预期。
- 参数是否准确，例如服务名、路径、命令。
- Agent 是否说明了操作目的和影响。
- 是否有备份、回滚或替代方案。
- 当前是否处于业务高峰或变更冻结期。

不确定时选择 `Reject`，并要求 Agent 继续只读诊断或给出更详细计划。

## 6. 安全机制

### 6.1 工具安全分级

系统将工具分为静态工具和可变工具：

| 类型 | 分级方式 |
|------|----------|
| 静态工具 | 工具注册时声明是否只读、是否可回滚。 |
| 可变工具 | 运行时按本次参数调用隐藏的伴生分类工具，判断是否可免审批。 |

只读工具通常自动执行；非只读工具默认需要人工审批。

### 6.2 规则判定顺序

管理员可通过 `web-server/config/rules.json` 管理工具级策略。判定顺序如下：

1. 命中 blacklist：拒绝执行。
2. 命中 whitelist：自动审批。
3. `is_read_only=true`：自动审批。
4. 其他情况：进入人工审批。

规则引擎只按工具名匹配，不做参数级判断。参数级风险由 tool-server 的伴生分类工具负责。伴生分类工具不展示给 LLM，web-server 在审查阶段隐式调用；分类失败时不会自动放行。

### 6.3 分层安全护栏

系统通过多个相互独立的检查点降低误操作风险：

| 层级 | 作用 |
|------|------|
| 输入安全门 | 在 LLM 推理前拦截四类高置信提示词注入，异常时保守拒绝。 |
| web-server 审查层 | 统一拦截工具调用，执行规则匹配和审批流转。 |
| 参数分类 | 对 Bash 命令的结构、参数、路径、重定向和网络访问进行检查。 |
| 人工审批 | 非只读和高风险操作必须等待用户批准。 |
| tool-server 二次校验 | 执行前校验审批状态、`request_id` 和跨服务 `auth_token`。 |
| 审计与异常处理 | 记录输入拒绝、策略决定、工具失败和异常路径。 |

### 6.4 审批超时

审批默认等待 300 秒。超时后审批状态变为 `EXPIRED`，工具不会执行，Agent 会收到审批过期结果并继续或结束当前分析。

### 6.5 最小权限

tool-server 以 Docker 容器方式运行，通过挂载范围和 Linux capabilities 限制访问权限。生产配置中应只授予实际需要的挂载点和能力。

eBPF、宿主 PID 和部分诊断命令可能需要较高权限。部署时应按诊断范围收紧配置，并以实际容器参数为准，不能仅凭“容器化”判断已经满足所有最小权限要求。

## 7. 管理员配置

### 7.1 配置文件目录

系统启动前需要准备 `web-server/config/`：

```text
web-server/config/
  servers.json
  rules.json
  llm.json
```

### 7.2 MCP Server 配置

`servers.json` 示例：

```json
[
  {
    "name": "tool-server",
    "url": "http://tool-server:11451/mcp",
    "transport": "streamable-http"
  }
]
```

本地或通用 Compose 环境中，web-server 通过容器内部 DNS 访问 tool-server。麒麟远程服务器使用 runbook 规定的容器网络和启动脚本。

架构具备云平台接入能力，可通过新增 MCP Server 扩展云资源查询与运维。管理员部署符合 MCP 协议的云资源服务后，将其名称和地址追加到 `servers.json`；web-server 会统一发现工具、保留服务归属，并把后续调用路由到对应 MCP Server。查询类工具可以声明为只读，运维变更类工具可以沿用动态分类和人工审批机制。

### 7.3 LLM 配置

`llm.json` 示例：

```json
{
  "api_key": "your-api-key",
  "api_url": "https://api.openai.com/v1",
  "model": "deepseek-v4-pro",
  "summary_model": "deepseek-v4-flash"
}
```

字段说明：

| 字段 | 说明 |
|------|------|
| api_key | OpenAI 兼容模型服务密钥。 |
| api_url | OpenAI 兼容 API 地址。 |
| model | 默认诊断模型。 |
| summary_model | 上下文压缩使用的轻量模型；不配置时复用 model。 |

前端请求可以携带 `model` 字段覆盖默认模型，具体取决于接入方是否开放该能力。

### 7.4 安全规则配置

`rules.json` 示例：

```json
{
  "whitelist": [
    {
      "tool_name": "delete_temp_files",
      "description": "原本需用户确认，加入白名单后自动审批通过"
    }
  ],
  "blacklist": [
    {
      "tool_name": "reboot_system",
      "description": "高危工具，禁止使用"
    }
  ],
  "input_safety": [
    {
      "id": "bypass_approval_controls",
      "patterns": [
        "(?:绕过|跳过).{0,40}(?:审批|确认|安全检查)"
      ],
      "reason": "检测到试图绕过审批或安全控制的提示注入"
    }
  ]
}
```

配置建议：

- 白名单只加入已充分评估、参数风险可控的工具。
- 黑名单用于禁止不符合组织策略的高危工具。
- 对 bash 等可变工具不要仅依赖工具名白名单，应结合实际风险审慎配置。
- 输入安全规则应同时准备命中样本和正常表达样本，避免扩大规则后误拦截合法运维请求。
- 修改规则后建议重新启动或按部署方式刷新 web-server 配置。

### 7.5 环境变量

常用环境变量：

| 变量 | 说明 |
|------|------|
| `LOG_LEVEL` | 应用日志级别。 |
| `DATABASE_URL` | PostgreSQL 连接地址，web-server 必填。 |
| `TOOLSERVER_SHARED_SECRET` | web-server 与 tool-server 之间的共享密钥；生产 Compose 必填，tool-server 绑定非 loopback 地址时也必填。 |
| `AGENT_MAX_ITERATIONS` | 单轮 Agent 最大迭代轮次，默认 30。 |
| `AGENT_TOKEN_CEILING_RATIO` | Token 硬上限比例，默认模型窗口的 95%。 |
| `ALASCUP_PROFILE` | 设置为 `1` 时启用检查点剖析器。 |
| `ALASCUP_AGENT_TRACE` | 设置为 `1` 时启用 Agent 调试日志。 |
| `ALASCUP_AGENT_TRACE_LEVEL` | 调试日志级别。 |
| `ALASCUP_AGENT_TRACE_FILTER` | 调试日志关键词过滤。 |

## 8. 部署与验证

## 9. 审计与追溯

### 9.1 可追溯内容

系统会记录：

- 用户输入和 Agent 回复。
- Agent 推理内容。
- 工具调用名称、参数、所属服务和读写属性。
- 审批请求、审批结果、审批备注和超时。
- 工具执行状态、结果和错误信息。
- Agent 状态变更，例如审批等待、审批通过、上下文压缩、错误退出。
- LLM 调用模型、token 消耗、延迟和响应内容。

### 9.2 常用数据库表

| 表 | 用途 |
|------|------|
| `chat_sessions` | 会话元数据。 |
| `messages` | 消息历史。 |
| `tool_calls` | 工具生命周期记录。 |
| `audit_events` | 不可变审计事件。 |
| `llm_traces` | LLM 调用追踪。 |

### 9.3 追溯建议

排查某次异常操作时，建议按以下顺序查看：

1. 根据时间、用户反馈或会话标题定位 `chat_sessions`。
2. 查看 `messages` 还原用户意图和 Agent 回复。
3. 查看 `tool_calls` 确认工具参数、审批状态和执行状态。
4. 查看 `audit_events` 追溯策略决策、审批决策和错误事件。
5. 必要时查看 `llm_traces` 分析模型输入输出和 token 使用情况。

## 10. 常见问题

### 10.1 页面提示 Connection lost 怎么办？

可能是网络中断、后端服务重启或 SSE 连接异常。可以刷新页面后重新打开会话，再发送一条消息继续处理。若频繁出现，请检查 frontend 到 web-server 的代理、web-server 日志和网络连通性。

### 10.2 Agent 一直分析但没有结论怎么办？

系统有最大迭代轮次限制，默认 30 轮。若触发 `Turn limit reached`，请重新发送更明确的问题，例如限制时间范围、服务名、日志路径或目标现象。

### 10.3 审批卡片消失或超时怎么办？

审批默认 5 分钟超时。超时后工具不会执行。可以重新发送请求，让 Agent 再次生成操作计划和审批请求。

### 10.4 为什么只读命令也可能要求审批？

bash 命令会经过严格分类。包含敏感路径、重定向、命令替换、网络访问、shell wrapper、复杂控制结构或可写 flag 时，会被判定为需要审批或拒绝。这样可以避免表面只读但实际存在副作用的命令绕过安全控制。

### 10.5 为什么工具执行失败？

常见原因包括：

- 工具参数错误，例如路径、服务名或命令不存在。
- tool-server 权限不足或挂载范围不包含目标资源。
- MCP 连接失败或超时。
- 审批状态不合法。
- 命中安全规则或二次校验失败。

请查看聊天中的 Failed 信息，并结合 web-server、tool-server 日志和 `audit_events` 排查。

### 10.6 为什么历史会话中看不到已删除会话？

删除会话是软删除，前端会话列表只显示未删除会话。底层审计数据不会因为普通删除操作而移除。

### 10.7 为什么上下文过大？

长会话、超长工具结果或大量日志会占用模型上下文。系统会先尝试截断工具结果和摘要早期消息；如果仍超过硬上限，会显示 `Context too large`。建议新建会话，并只带入关键结论继续。

### 10.8 为什么请求被提示词注入规则拦截？

消息可能包含“忽略安全规则”“泄露 system prompt”“读取密钥”或“绕过审批”等高置信模式。系统会在调用 LLM 前结束本轮，并记录命中的规则。若这是合法的安全检查请求，请改为描述检查目标，例如“检查日志中是否意外输出凭据，但不要显示凭据内容”。

### 10.9 为什么工具结果刷新后仍然可以查看？

工具调用和结果会写入 `tool_calls`。加载历史会话时，前端将持久化结果转换为与实时 SSE 相同的数据结构，因此字符串、对象、数组和数值结果都可以恢复。点击工具证据卡即可展开查看。

## 11. 使用建议

- 先诊断，后操作。让 Agent 先用只读工具收集证据，再讨论修复。
- 对删除、重启、写入配置、批量清理等操作，要求 Agent 先输出计划和影响说明。
- 审批前仔细检查工具参数，尤其是路径、服务名和 shell 命令。
- 日志读取尽量指定时间范围、关键词或最大行数。
- 长问题拆成多轮处理，避免一次性要求 Agent 同时诊断和修复多个无关问题。
- 生产环境谨慎配置 whitelist，优先保持高风险操作人工审批。
