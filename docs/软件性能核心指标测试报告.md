## 1. 测试目的

本报告记录 Alascup Agent 当前版本的核心性能基线，重点检查安全校验、API 应用层、命令分类和系统感知是否引入明显额外延迟。

智能运维请求的总耗时通常由 LLM 网络响应、MCP 网络、目标系统命令和 eBPF 采样窗口共同决定。本次先测量可稳定复现的本地组件；真实模型、容器网络、PostgreSQL 和 LoongArch/麒麟实机数据单独列为待测项，不与本地应用内基线混用。

## 3. 指标与方法

| 指标 | 样本 | 方法 |
|---|---:|---|
| `/api/health` 应用层延迟 | 2,000 | ASGI 内进程请求，数据库查询使用立即返回的模拟依赖，工具数固定为 18 |
| `/api/metrics` 应用层延迟 | 2,000 | ASGI 内进程请求，读取全局阶段耗时聚合 |
| 输入安全门延迟 | 20,000 | 4 条中英文正常/风险消息轮询执行 |
| Bash 分类延迟 | 12,000 | 3 条只读命令和 3 条高风险命令轮询执行 |
| CPU 感知延迟 | 20 | 读取 `/proc/cpuinfo`，调用 `psutil.cpu_percent(interval=0.1)` |

每项测试先预热，再记录平均值、P50、P95 和最大值。时间单位为毫秒。

健康接口的生产代码同时检查 PostgreSQL 和已发现工具数。本次基线用模拟数据库隔离外部网络开销，测量的是 FastAPI 路由与业务判断本身。

源码：`web-server/src/api/health.py`

```python
@router.get("/health")
async def health(
    db=Depends(db_dep),
    executor=Depends(tool_executor),
):
    checks: dict[str, str] = {}

    # PostgreSQL connectivity
    try:
        await db.fetchrow("SELECT 1")
        checks["postgres"] = "ok"
    except Exception:
        checks["postgres"] = "error"

    # Tool discovery
    tools = executor.list_tools()
    checks["tools_discovered"] = str(len(tools))

    status = "ok" if checks.get("postgres") == "ok" else "degraded"
    return {"status": status, "checks": checks, "version": "0.1.0"}
```

| 测试项 | 样本 | 平均值 | P50 | P95 | 最大值 |

| 接口 | 吞吐量 |

## 5. 结果分析

### 5.1 输入安全门

输入检查 P95 为 0.0056 ms。与 LLM 网络调用相比，这部分开销可以忽略。安全门放在 LLM 前不会形成可感知等待，却能在风险请求进入模型前结束本轮。

2 万次测试包含正常消息和三类被拦截消息，共得到 5,000 次 `ALLOW` 和 15,000 次 `BLOCK`。该比例来自固定样本构成，不代表生产流量中的风险比例。

### 5.2 Bash 参数分类

Bash 分类 P95 为 0.0412 ms。样本中 6,000 次判定为可免审批只读，6,000 次判定为需要审批。AST 解析和规则检查的时间远低于命令实际执行时间，适合在每次可变工具调用前执行。这使系统可以按本次命令动态判断风险，而不必在安全性和诊断效率之间使用粗粒度的固定标签。

### 5.3 CPU 感知

CPU 工具 P50 为 100.6030 ms。代码显式使用 0.1 秒采样窗口，测试结果与设计一致；这不是解析器或 IPC 带来的额外延迟。该采样能够提供比瞬时读取更有意义的 CPU 利用率。

源码：`tool-server/src/tools/perception/cpu.py`

```python
def get_cpu_info(config: ToolServerConfig) -> dict:
    model_name = _read_model_name(config.proc_path)

    return {
        "cpu_percent": psutil.cpu_percent(interval=0.1),
        "cores": psutil.cpu_count() or 1,
        "model_name": model_name,
        "loadavg": list(psutil.getloadavg()),
    }
```

### 5.4 健康与指标接口

`/api/health` 和 `/api/metrics` 的 P95 均低于 0.5 ms。`/api/metrics` 出现一次 59.4444 ms 最大值，但 P95 仍为 0.3025 ms，判断为本地调度抖动，不影响主体分布。

健康接口的真实部署延迟还会包含 PostgreSQL `SELECT 1` 和反向代理网络时间，因此答辩时应优先使用实机 `curl` 数据补充本报告。

## 7. 影响端到端耗时的设计

- 静态只读工具可以并行预执行，避免逐个等待独立感知工具。
- SSE 持续返回 reasoning、assistant、工具和审批状态，用户无需等待整轮结束才看到进展。
- Agent 设置最大迭代轮次和 token 硬上限，防止任务无限运行。
- MCP 仅对连接错误执行有限重试；运行时错误直接返回，避免重复产生副作用。
- 新增云平台 MCP Server 复用统一发现、服务路由、风险审查、超时和并行执行机制，不增加 Agent 主循环分支。
- eBPF 工具有明确采样时长和超时，例如系统调用统计默认 5 秒，I/O 延迟默认 10 秒。
- `/api/metrics` 提供功能阶段平均耗时，`ALASCUP_PROFILE=1` 可记录单次请求检查点。

只读工具并行不是文档层面的优化设想。执行器为每个调用创建协程，并通过 `asyncio.gather` 等待全部结果。

架构具备云平台接入能力，可通过新增 MCP Server 扩展云资源查询与运维。云资源查询工具可以与本地感知工具一起进入并行队列；需要变更资源状态的工具则复用现有审查和审批链路。扩展服务只改变工具目录和调用目标，不改变 Agent 的迭代路径。

源码：`web-server/src/mcp_client/executor.py`

```python
async def execute_parallel(self, calls: list[dict]) -> list[dict]:
    tasks = [
        self.execute(
            c["tool_name"],
            c.get("arguments", {}),
            server_name=c["server_name"],
            approval_status=c.get("approval_status", "APPROVED"),
            request_id=c.get("request_id", ""),
            chat_id=c.get("chat_id", ""),
        )
        for c in calls
    ]
    return await asyncio.gather(*tasks)
```

## 8. 当前未覆盖指标

以下数据需要目标环境或外部服务，当前报告不做推断：

- LoongArch + 麒麟高级服务器版 V11 的接口 P50/P95、CPU 和内存占用。
- 真实 PostgreSQL、Nginx 和 MCP 网络下的端到端延迟。
- 真实 LLM 的首 token、完成耗时、token 消耗和错误率。
- 多用户并发、长连接上限和 24 小时稳定性。
- eBPF 在真实故障事件下的采样开销。
- 高风险审批从发起到人工决定的业务耗时。

这些指标应在最终演示环境中复测，并将硬件、模型、网络和样本量与结果一起记录。

## 10. 结论

本地基线表明，入口安全检查和 Bash 参数分类的 P95 分别为 0.0056 ms 和 0.0412 ms，没有成为 Agent 主流程的性能瓶颈。CPU 感知约 100 ms，主要来自主动采样窗口。健康和指标接口的应用层 P95 低于 0.5 ms。

当前架构已经具备低成本安全校验、只读并行、流式反馈和多 MCP Server 扩展能力。Bash 动态分类可以高频执行；云资源查询与运维也可以通过新增 MCP Server 接入统一工具链。最终提交前应在 LoongArch/麒麟 V11 环境补充真实数据库、MCP、LLM 和容器网络下的端到端数据，形成目标平台版本的最终性能附件。
