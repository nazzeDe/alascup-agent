## 1. 设计目标

Alascup Agent 的设计重点是让大模型负责理解和规划，让确定性的工程模块负责风险判断、审批、执行与留痕。系统不允许 LLM 直接越过策略层调用宿主能力。

设计需要同时满足三件事：能够读取足够多的系统证据；写操作始终受控；发生异常后可以沿会话和工具调用记录还原过程。

## 2. 总体架构

```text
Browser / Vue 3
    -> Nginx
        -> FastAPI web-server
            -> InputSafetyGate
            -> ReAct Agent loop
            -> RuleEngine / ApprovalBridge
            -> MCP Client
                -> ServerRegistry
                    -> FastMCP tool-server
                        -> OS / PostgreSQL / eBPF / Bash
                    -> Cloud MCP Server（扩展）
                        -> 云资源查询 / 运维操作
            -> PostgreSQL
                -> sessions / messages / tool_calls
                -> audit_events / llm_traces
```

系统采用 B/S 架构。frontend 负责交互和证据展示；web-server 负责会话、推理编排、安全决策、MCP 多服务路由和审计；tool-server 负责工具注册、参数级分类和受控执行；PostgreSQL 保存业务与追踪数据。具体基础设施能力位于 MCP Server 侧，Agent 主循环不与某个操作系统工具或云平台 API 绑定。

## 3. 服务职责

### 3.1 frontend

- Vue 3 + TypeScript 单页应用，使用 Nginx 提供静态资源。
- 通过 REST 管理会话和审批，通过 SSE 接收本轮实时事件。
- 展示用户消息、推理摘要、工具证据、审批请求、执行结果和错误。
- 使用 DTO 适配层统一历史 REST 与实时 SSE 的工具结果格式。
- 对 Markdown 输出先清洗再渲染，降低脚本注入风险。

### 3.2 web-server

- FastAPI 提供 `/api/chat`、会话、审批、健康、指标和工具目录接口。
- `InputSafetyGate` 在构建 LLM 状态前检查用户输入。
- ReAct 循环按 `think -> review -> act -> observe` 运行。
- 所有工具调用进入统一审查入口，不能由 LLM 绕过。
- `ServerRegistry` 发现多个 MCP Server，并保存工具到服务的路由关系。
- 高风险调用通过 `ApprovalBridge` 等待用户决定。
- 会话、工具生命周期、审计和 LLM trace 写入 PostgreSQL。

### 3.3 tool-server

- FastMCP 注册 18 个业务工具和内部执行工具。
- 静态工具在注册时声明只读、可回滚和可变更元数据。
- Bash 等可变工具使用伴生分类器检查本次参数。
- 实际执行统一进入隐藏的 `execute_tool`，校验鉴权、请求 ID 和审批状态。
- eBPF 工具根据内核环境选择探针，返回结构化事件。

### 3.4 PostgreSQL

- `chat_sessions`：会话元数据和软删除状态。
- `messages`：用户、助手和工具相关消息。
- `tool_calls`：工具参数、风险属性、审批、结果和错误。
- `audit_events`：只追加的策略与执行事件。
- `llm_traces`：模型、prompt、completion、token 和延迟。

## 5. 核心处理流程

### 5.1 输入阶段

1. frontend 向 `POST /api/chat` 发送用户消息。
2. web-server 创建或加载会话，并发送 `session_init`。
3. `InputSafetyGate` 对规范化后的文本逐条匹配安全规则。
4. 命中规则时返回 `PROMPT_INJECTION_BLOCKED`，记录 `INPUT_REJECTED`，不调用 LLM。
5. 通过检查后，系统构建历史消息、system prompt 和工具目录。

### 5.2 诊断阶段

1. LLM 生成文本或工具调用。
2. 静态只读工具可以并行预执行。
3. 可变工具先调用 `{tool_name}_classify` 获取本次风险属性。
4. 工具结果以 `tool_result` 返回 Agent，Agent 根据证据继续分析。
5. 已完成故障诊断时，最终回答使用六段式 RCA 结构。

### 5.3 高风险操作阶段

1. RuleEngine 判断调用需要审批。
2. web-server 持久化工具生命周期并发送 `tool_approval_required`。
3. 用户通过 REST 提交批准或拒绝，后端校验 `request_id + chat_id`。
4. 批准后，web-server 调用 tool-server 的 `execute_tool`。
5. tool-server 再次校验审批、请求绑定和共享鉴权，然后执行真实工具。
6. 拒绝、超时、失败和成功结果都返回 LLM，并写入工具记录和审计。

## 6. 安全架构

安全控制分布在六个检查点，任何一个环节都不能单独代表完整安全能力。

| 检查点 | 设计 |
|---|---|
| 用户输入 | 四类中英文提示词注入规则，Unicode NFKC 规范化，异常 fail closed |
| 工具元数据 | 静态声明只读、可回滚和可变更属性 |
| 参数级分类 | Bash AST 解析，检查命令、flag、路径、重定向和网络访问 |
| 策略决策 | blacklist、whitelist、只读自动批准、默认人工审批 |
| 执行入口 | `approval_status`、`request_id`、`chat_id` 和共享鉴权校验 |
| 审计 | 输入拒绝、策略决定、审批和执行状态持久化 |

输入规则用于降低已知高置信注入风险，不宣称覆盖所有语义改写或编码攻击。工具分类中的 `safe=false` 表示不能免审批，不等同于无条件禁止；真正禁止的工具由 blacklist 决定。

策略顺序直接固化在 `RuleEngine` 中，blacklist 优先于 whitelist 和只读属性。接口很短，决策顺序也容易审计。

源码：`web-server/src/security/rule_engine.py`

```python
def evaluate(
    self, tool_name: str, is_read_only: bool, is_rollbackable: bool
) -> str:
    if tool_name in self._blacklist:
        return "REJECT"
    if tool_name in self._whitelist:
        return "AUTO_APPROVE"
    if is_read_only:
        return "AUTO_APPROVE"
    return "REQUIRE_APPROVAL"
```

## 7. MCP 工具设计

当前共有 18 个面向业务的工具：

| 类别 | 数量 | 能力 |
|---|---:|---|
| 基础系统感知 | 5 | CPU、内存、磁盘、网络、进程 |
| 工具服务运行态 | 2 | tool-server 状态、tool-server 日志 |
| PostgreSQL | 2 | schema、只读查询 |
| 受控操作 | 1 | Bash |
| eBPF | 8 | 进程启动/退出、TCP 连接、系统调用、慢调用、TCP 丢包、I/O 延迟、OOM |

`execute_tool`、`health` 和 `bash_classify` 是内部工具，不计入业务工具数量。受控 Bash 可以补充 `lsof`、`netstat`、`journalctl` 和 `systemctl status` 等系统诊断能力。

工具的安全属性与 schema 在注册时一起声明。只读 CPU 工具和可变 Bash 工具使用同一 MCP 注册机制，但元数据不同，审查层无需靠工具名称猜测风险。

源码节选（两个代表性工具的注册段落）：`tool-server/src/tool_catalog.py`

```python
@server.tool(
    name="get_cpu_info",
    description="获取 CPU 型号、核心数、负载和利用率",
    output_schema=_ANY_OBJECT,
    meta={"is_read_only": True, "is_rollbackable": True, "mutable": False},
)
def _get_cpu_info() -> dict:
    return get_cpu_info(config)

@server.tool(
    name="bash",
    description="在沙箱环境中执行 Shell 命令",
    output_schema=_ANY_OBJECT,
    meta={"is_read_only": False, "is_rollbackable": False, "mutable": True},
)
def _bash(command: str = "", timeout: int | None = None) -> dict:
    return run_bash(config, command=command, timeout=timeout)
```

### 7.1 动态伴生分类

Bash 的风险不是静态属性。同一个工具调用 `ls /tmp` 时可以是只读诊断，调用删除、重定向或网络命令时则需要审批。tool-server 因此为可变工具自动注册隐藏的 `{tool_name}_classify`；web-server 在每次工具审查中按本次参数调用它，分类失败一律按 `safe=false` 处理。

源码：`tool-server/src/tool_catalog.py`

```python
for tool_name, classify_fn in classify_fns.items():
    factory = companion_factory.get(tool_name)
    if factory is None:
        continue

    server.tool(
        name=f"{tool_name}_classify",
        description=f"Security classification companion for {tool_name}",
        meta={"hidden": True, "is_read_only": True, "mutable": False},
    )(factory(classify_fn))
```

`hidden=true` 使伴生工具不进入 LLM 工具列表。审查层知道命名约定，可以直接调用对应 MCP 方法，模型既不需要理解分类器，也不能选择跳过分类步骤。

源码：`web-server/src/mcp_client/executor.py`

```python
result = await client.call_tool(
    f"{tool_name}_classify",
    params,
)
content = getattr(result, "content", None)
if isinstance(content, list) and content:
    try:
        data = json.loads(getattr(content[0], "text", "{}"))
        return {"safe": data.get("safe", False)}
    except (json.JSONDecodeError, AttributeError):
        return {"safe": False}
return {"safe": False}
```

### 7.2 多 MCP Server 与云平台接入

架构具备云平台接入能力，可通过新增 MCP Server 扩展云资源查询与运维。`ServerRegistry` 遍历全部已配置服务，发现工具后写入 `server_name`、参数 schema 和安全元数据；执行器再按 `server_name` 路由到对应服务。因此，接入云资源只需增加 MCP Server 配置和工具实现，Agent 的 `think -> review -> act -> observe` 主循环保持不变。

源码核心结构（省略连接重试与日志分支）：`web-server/src/mcp_client/registry.py`

```python
async def discover(self) -> list[dict]:
    all_tools: list[dict] = []
    for entry in self._servers.values():
        server_tools = await self._fetch_tools(entry)
        all_tools.extend(server_tools)
    self._tools = all_tools
    return all_tools

# _fetch_tools() 中记录所属 MCP Server
tools.append(
    {
        "name": t.name,
        "server_name": entry.name,
        "params_schema": getattr(t, "inputSchema", None) or {},
        "mutable": meta.get("mutable", False),
        "is_read_only": meta.get("is_read_only", False),
        "is_rollbackable": meta.get("is_rollbackable", False),
    }
)
```

独立的只读调用由 `asyncio.gather` 并行执行。该设计在多指标诊断时减少串行等待，同时保留每个调用自己的结果和错误。

源码：`web-server/src/mcp_client/executor.py`

```python
async def execute_parallel(self, calls: list[dict]) -> list[dict]:
    tasks = [
        self.execute(
            c["tool_name"],
            c.get("arguments", {}),
            server_name=c["server_name"],
            approval_status=c.get("approval_status", "APPROVED"),
            request_id=c.get("request_id", ""),
            chat_id=c.get("chat_id", ""),
        )
        for c in calls
    ]
    return await asyncio.gather(*tasks)
```

## 8. 前端证据设计

工具卡摘要展示：

- R/W 属性。
- 工具名称。
- 审批状态。
- 执行状态。
- 执行耗时。

展开后展示 MCP Server、回滚属性、完整参数、结果预览和错误。结果预览最多 20 行或 16 KiB，完整内容仍可复制。该限制只影响界面展示，不改写持久化结果。

历史会话通过 `SessionDtoAdapter` 将持久化 `result` 信封转换为前端 `output`，支持任意 JSON 值。这样可以保证实时会话和刷新后的历史会话显示一致。

源码：`frontend/vue-project/src/infrastructure/session-dto-adapter.ts`

```typescript
function toToolCallInfo(dto: ToolCallDto): ToolCallInfo {
  const { result, ...toolCall } = dto
  if (result === undefined) return toolCall
  if (!isToolResultDto(result)) return { ...toolCall, output: result }

  return {
    ...toolCall,
    ...(Object.prototype.hasOwnProperty.call(result, 'output') ? { output: result.output } : {}),
    ...(!toolCall.error && result.error ? { error: result.error } : {}),
    ...(toolCall.execution_time_ms === undefined && result.execution_time_ms !== undefined
      ? { execution_time_ms: result.execution_time_ms }
      : {}),
  }
}
```

## 9. Prompt 与根因分析设计

System prompt 按以下顺序组装：

```text
identity -> rules -> tool_usage -> diagnostic_reporting -> environment -> memory
```

`diagnostic_reporting` 只在完成故障诊断且已有工具证据时生效。报告包含根因结论、关键证据、置信度、备选原因、影响范围、处置建议与风险。普通对话保持简短。

源码：`web-server/src/services/prompt_manager.py`

```python
DEFAULT_DIAGNOSTIC_REPORTING = (
    "故障诊断报告规范：\n"
    "- 仅在完成故障诊断且已有工具证据时，最终回答使用以下 Markdown 结构：\n"
    "  ## 根因结论\n"
    "  ## 关键证据\n"
    "  ## 置信度\n"
    "  ## 备选原因\n"
    "  ## 影响范围\n"
    "  ## 处置建议与风险\n"
    "- 普通对话（包括问候、能力介绍和纯操作确认）保持简短，不套用上述结构"
)
```

## 10. 通信协议

| 通信路径 | 协议 | 用途 |
|---|---|---|
| Browser -> frontend | HTTP | 静态资源 |
| frontend -> web-server | REST + SSE | 会话、审批、实时聊天 |
| web-server -> tool-server | MCP / JSON-RPC | 工具发现、分类与执行 |
| web-server -> LLM | OpenAI 兼容 HTTP API | 推理、流式输出、上下文摘要 |
| web-server -> PostgreSQL | PostgreSQL 协议 | 会话、审计和 trace |

主要 SSE 事件包括 `session_init`、`reasoning`、`assistant`、`tool_call`、`tool_result`、`tool_approval_required`、`error` 和 `done`。每个已展示的 `tool_call` 必须有同一 `call_id` 的结束结果，避免前端状态悬空。

## 11. 性能与可靠性设计

- 静态只读工具并行预执行，减少多工具诊断等待时间。
- SSE 在同一连接中持续返回文本、工具和审批状态。
- Context Manager 在接近 token 上限时压缩早期消息。
- MCP 连接错误执行有限重试；工具运行错误不做无界重试。
- Agent 有最大轮次和 token 硬上限。
- `/api/metrics` 聚合功能阶段平均耗时，`ALASCUP_PROFILE=1` 可记录单次检查点。

## 12. 部署设计

本地与通用环境可使用项目 Compose 配置。麒麟远程服务器使用预构建镜像和 runbook 脚本，不在远程运行 Bun/npm 构建，也不使用 `docker compose`。

tool-server 的宿主挂载以只读为主。eBPF、PID namespace 和宿主诊断需要的 capabilities 按部署模式配置；权限说明以实际容器配置为准。
