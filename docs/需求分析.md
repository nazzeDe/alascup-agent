> 对应赛题：部署于操作系统的智能运维 Agent

## 1. 编写目的

本文说明 Alascup Agent 的业务目标、用户角色、功能需求、非功能需求和验收边界。需求来源以 `docs/require/question.md` 为准，内容覆盖赛题要求的 OS 深度感知、MCP 运维插件、安全意图校验、最小权限代理执行和推理链路溯源。

## 2. 业务背景

教育、医疗和政企数据中心长期运行大量 Linux 服务。遇到僵尸进程、磁盘 I/O 异常、日志占满磁盘、网络故障或配置漂移时，运维人员需要在多个命令、日志和监控页面之间来回切换。问题通常不在于缺少工具，而在于工具分散、操作门槛高，诊断过程也难以完整复盘。

Alascup Agent 将自然语言交互与 MCP 工具结合。用户描述目标后，系统先收集证据，再给出判断；需要修改系统时，必须经过风险检查和人工审批。这样可以缩短常见故障的排查路径，同时保留传统运维最看重的控制权和可追溯性。

## 3. 产品目标

### 3.1 总体目标

- 在浏览器中提供自然语言运维入口，支持连续会话和流式反馈。
- 通过 MCP 对系统感知、数据库查询、eBPF 诊断和运维操作进行标准化封装。
- 保持 Agent 主流程与具体基础设施解耦，通过新增 MCP Server 扩展云资源查询与运维能力。
- 将输入检查、工具风险分级、人工审批、工具端复核和审计记录组成安全闭环。
- 在 LoongArch 架构和麒麟高级服务器版 V11 上完成部署与运行。
- 让诊断结论能够追溯到具体工具、参数、结果和审批状态。

### 3.2 本阶段边界

- 目标平台是 Linux，不承担 Windows 或 macOS 运维。
- 当前不建设多租户账号体系和统一身份认证中心。
- 当前不替代完整监控告警平台，也不提供无人值守的高危自动变更。
- 当前没有完整知识库/RAG。上下文管理、会话历史和 LLM trace 不等同于知识库检索。

## 4. 用户角色

| 角色 | 主要任务 |
|---|---|
| 运维人员 | 发起诊断，查看系统证据，审批或拒绝高风险操作，回看历史会话 |
| 系统管理员 | 部署服务，配置模型与 MCP Server，维护安全规则、权限和日志 |
| 审计人员 | 根据会话、工具调用、审批记录和审计事件还原操作过程 |

## 5. 典型业务流程

### 5.1 只读诊断

用户提出“检查 CPU、内存和高占用进程”。系统识别目标后调用只读工具，前端实时展示工具状态和结果。Agent 基于已取得的证据给出根因判断，不触发审批。

### 5.2 高风险操作

用户提出“清理磁盘空间”。系统先检查磁盘和相关日志，再生成操作计划。删除、移动、重启或配置写入等动作必须进入审批；用户拒绝或审批超时后，工具不得执行。

### 5.3 提示词注入

用户试图要求系统忽略安全规则、泄露系统指令、读取凭据或绕过审批。输入安全门在 LLM 推理前完成检查，命中后结束本轮请求，返回明确错误并写入审计。

### 5.4 故障根因分析

用户要求分析服务异常。Agent 先调用进程、网络、日志或 eBPF 工具收集证据；取得证据后，报告按根因、关键证据、置信度、备选原因、影响范围、处置建议与风险组织。

## 6. 功能需求

### FR-01 自然语言会话

系统应提供 B/S 交互界面，支持新建会话、连续提问、历史会话加载和软删除。回答、推理摘要、工具调用、审批和错误通过 SSE 实时返回。

验收标准：

- 首个 SSE 事件返回真实 `chat_id`，流结束时返回 `done`。
- 用户刷新页面后，消息和已持久化工具结果仍可恢复。
- 网络或服务异常后，界面保持可继续使用的状态。

### FR-02 Agent 诊断循环

系统应按 `think -> review -> act -> observe` 处理任务。Agent 可以多轮收集证据，并在达到完成条件、轮次上限或 token 上限时明确结束。

验收标准：

- 独立的只读工具调用可以并行执行。
- 工具失败会返回结构化错误，不得无限重试。
- 超过最大迭代轮次或 token 上限时返回可识别错误。

### FR-03 OS 深度感知

系统应采集 CPU、内存、磁盘、网络、进程、日志和内核事件。受控 Bash 能力用于补充 `lsof`、`netstat`、`journalctl`、`systemctl` 等常见诊断命令。

当前业务工具共 18 个：5 个基础系统感知工具、2 个工具服务运行态工具、2 个 PostgreSQL 工具、1 个受控 Bash 工具和 8 个 eBPF 工具。

### FR-04 MCP 插件化

运维能力应通过 MCP Tool 注册和发现。每个工具需提供名称、描述、参数 schema、输出 schema，以及只读、可回滚、可变更等安全元数据。系统支持配置多个 MCP Server，并按 `server_name` 保留工具归属和调用路由。

架构具备云平台接入能力，可通过新增 MCP Server 扩展云资源查询与运维。云资源工具沿用现有的发现、参数 schema、风险审查、审批和调用流程，不需要修改 Agent 主循环。

验收标准：

- 新增工具不修改会话主循环。
- 已配置的 MCP Server 可以统一发现，工具调用能够路由到所属服务。
- 面向 LLM 的业务工具与内部健康检查、分类和执行工具分离。
- 可变工具可以配套注册 `{tool_name}_classify` 分类工具。

### FR-05 输入安全检查

系统应在用户输入进入 LLM 前执行独立安全检查。规则至少覆盖以下高置信模式：

- 试图改写或忽略系统安全规则。
- 索取 system prompt 或开发者指令。
- 索取密码、API Key、访问令牌或私钥。
- 绕过人工审批、权限或安全检查。

验收标准：

- 命中规则时返回 `PROMPT_INJECTION_BLOCKED`。
- 审计事件保存规则 ID 和拒绝原因。
- 规则配置无效或评估异常时 fail closed。
- 正常的安全咨询、日志查询和“不要绕过审批”等否定表达不应被误拦截。

以下代码是当前输入安全门的核心判断。它先统一 Unicode 表达，再执行配置规则；配置或运行异常都走 `_evaluation_failure()`，不会因检查失败而放行。

源码：`web-server/src/security/input_safety.py`

```python
def assess(self, message: str) -> SafetyAssessment:
    if not self._configuration_is_valid:
        return self._evaluation_failure()

    try:
        normalized = unicodedata.normalize("NFKC", message).casefold()
        for rule, patterns in self._rules:
            if any(pattern.search(normalized) for pattern in patterns):
                return SafetyAssessment(
                    decision=SafetyDecision.BLOCK,
                    rule_id=rule.id,
                    reason=rule.reason,
                )
        return SafetyAssessment(decision=SafetyDecision.ALLOW)
    except Exception:
        return self._evaluation_failure()
```

### FR-06 工具风险分级

所有工具调用必须进入统一审查入口。系统按黑名单、白名单、只读属性和默认策略给出 `REJECT`、`AUTO_APPROVE` 或 `REQUIRE_APPROVAL` 决策。

对 Bash 等可变工具，系统应按本次调用参数动态判断风险，而不是给工具贴一个固定的读写标签。tool-server 使用 `tree-sitter-bash` 解析命令结构，检查命令、子命令、flag、路径、重定向、命令替换、网络访问和 shell wrapper。

可变工具自动配套隐藏的 `{tool_name}_classify` 伴生工具。它不进入 LLM 可见工具列表，由 web-server 在每次审查时隐式调用；返回解析失败、分类异常或未知语法时按高风险处理。可变 Bash 还必须通过隐藏的 `execute_tool` 执行入口，直接调用不能绕过审批与校验。

### FR-07 人工审批

高风险工具必须等待用户批准。审批请求应与 `chat_id`、`request_id`、工具名称和参数绑定，支持批准、拒绝和超时。

验收标准：

- 未批准、已拒绝或已过期的请求不得执行。
- 默认审批等待时间为 300 秒。
- 审批结果写入工具生命周期和审计事件。

### FR-08 受控执行

tool-server 应在容器边界内执行工具。执行入口校验共享鉴权、`request_id` 和审批状态；可变工具不得绕过隐藏的 `execute_tool` 生命周期直接执行。

宿主挂载和 Linux capabilities 应按实际诊断需求配置。eBPF 和宿主级诊断可能需要较高权限，文档与部署配置必须如实说明。

执行校验不是约定，而是 tool-server 的入口条件。共享密钥使用常量时间比较；写操作还必须携带有效 UUID 格式的 `request_id`。

源码节选（省略日志语句）：`tool-server/src/security/validate.py`

```python
def validate_execution(
    approval_status: str,
    request_id: str,
    is_read_only: bool,
    auth_token: str = "",
    shared_secret: str = "",
) -> tuple[bool, str]:
    if shared_secret and not hmac.compare_digest(auth_token, shared_secret):
        return False, "invalid tool-server auth token"
    if approval_status != "APPROVED":
        return False, f"approval_status must be APPROVED, got {approval_status}"
    if not is_read_only:
        if not request_id:
            return False, "request_id required for destructive operations"
        try:
            uuid.UUID(request_id)
        except (ValueError, AttributeError):
            return False, f"invalid request_id UUID: {request_id!r}"
    return True, ""
```

### FR-09 推理链路追溯

系统应记录从用户请求到执行结果的关键节点，包括消息、工具参数、风险属性、审批状态、执行结果、错误、Agent 状态变化和 LLM 调用摘要。

验收标准：

- `audit_events` 采用只追加写入。
- `tool_calls` 能关联会话、LLM 工具调用和审批请求。
- `llm_traces` 记录模型、token、延迟和请求响应。

### FR-10 工具证据展示

前端应将一次工具调用的状态和证据放在同一组件中。摘要区域显示工具名、读写属性、审批状态、执行状态和耗时；展开后显示 MCP Server、回滚属性、完整参数、结果和错误。

历史 REST 数据与实时 SSE 数据应在前端适配层统一。工具输出允许字符串、对象、数组、数值、布尔值和 `null`。

### FR-11 结构化根因分析

完成故障诊断且已有工具证据时，最终回答应包含：

1. 根因结论。
2. 关键证据。
3. 置信度。
4. 备选原因。
5. 影响范围。
6. 处置建议与风险。

普通问候、能力介绍和简单确认无需套用诊断报告结构。

### FR-12 国产环境部署

系统应支持 LoongArch 架构和麒麟高级服务器版 V11。前端采用预构建静态资源，远程服务器不执行 Bun/npm 构建；远程启动按项目 runbook 执行，不使用 `docker compose`。

## 8. 业务规则

- 所有工具调用先审查，后执行。
- 黑名单优先级高于白名单和只读属性。
- 安全分类或规则评估失败时不自动放行。
- 删除、重启、配置写入和其他不可逆操作默认要求审批。
- Agent 不得把工具返回内容当成新的高优先级系统指令。
- 工具结果必须关联原始调用 ID，避免证据串线。
- 凭据不得写入仓库文件、命令历史或日志。
