## 命名规范

所有数据结构字段、Python 变量、数据库列名统一使用 **snake_case**。JSON 序列化直接使用字段名，不做别名转换。

## 基础数据结构

### SafetyAssessment

```
SafetyAssessment {
  decision: string [ALLOW | BLOCK]
  rule_id: string | null
  reason: string | null
}
```

`InputSafetyGate` 在创建 AgentState 之前返回该结构。命中规则后，web-server 记录 `INPUT_REJECTED` 审计事件并发送 `PROMPT_INJECTION_BLOCKED`；规则编译失败或运行时评估异常时返回 `BLOCK`。

### Message

```
Message {
  message_id: string (UUID)
  chat_id: string (UUID)
  timestamp: string (RFC 3339)
  type: string [user | assistant | tool_call | tool_result | system]
  content: string
  tool_calls: object[] | null
  tool_call_id: string | null
  tool_name: string | null
  reasoning_content: string | null
}
```

| 字段 | 说明 |
|------|------|
| `type: user` | 用户输入 |
| `type: assistant` | LLM 文本回复；可携带 `tool_calls` 和 `reasoning_content` |
| `type: tool_call` | 兼容旧类型；当前运行时主要通过 assistant `tool_calls` 保存工具请求 |
| `type: tool_result` | 工具执行结果；`tool_call_id` 与 LLM tool call id 对齐 |
| `type: system` | 系统通知 |
| `reasoning_content` | DeepSeek thinking 模式要求回传的推理内容，不再使用 `is_meta` |

SSE 流式传输时工具调用和工具结果通过事件 data 获取结构化信息；加载历史时，web-server 将 `messages` 和必要的 `tool_calls` 记录投影为 LLM 可接受的 history。

### Tool

```
Tool {
  name: string
  server_name: string
  description: string
  params_schema: object
  mutable: boolean
  is_read_only: boolean
  is_rollbackable: boolean
}
```

tool-server 通过 fastmcp 工具元数据携带 `mutable`、`is_read_only`、`is_rollbackable`、`hidden` 等字段；web-server 的工具发现缓存将其展平为 LLM 和审查层使用的工具对象。

| 类型 | `mutable` | 分级方式 |
|------|-----------|----------|
| 静态工具 | `false` | 注册时声明 `is_read_only` / `is_rollbackable`，web-server 直接使用 |
| 可变工具 | `true` | 运行时调用伴生分类工具 `{tool_name}_classify`，返回 `{"safe": bool}` |

### 伴生分类工具

每个可变工具自动注册伴生 MCP 工具，命名规则为 `{tool_name}_classify`。伴生工具必须标记：

```
meta.hidden = true
meta.mutable = false
meta.is_read_only = true
```

`hidden=true` 的工具不会进入 LLM 可见工具缓存。web-server 按 `{tool_name}_classify` 命名约定直接调用所属 MCP Server，因此分类步骤由审查层隐式完成，不依赖模型主动选择。

伴生工具的注册、隐藏和调用分别落在三个位置：

```python
# tool-server/src/tool_catalog.py
server.tool(
    name=f"{tool_name}_classify",
    description=f"Security classification companion for {tool_name}",
    meta={"hidden": True, "is_read_only": True, "mutable": False},
)(factory(classify_fn))

# web-server/src/mcp_client/registry.py
meta = getattr(t, "meta", None) or {}
if meta.get("hidden"):
    continue

# web-server/src/mcp_client/executor.py
result = await client.call_tool(f"{tool_name}_classify", params)
```

### ToolCall

```
ToolCall {
  // 继承 Tool 的属性
  chat_id: string (UUID)
  message_id: string (UUID | null)
  call_id: string (UUID | null)          // web-server 内部生命周期 ID
  llm_trace_id: string (UUID | null)
  llm_tool_call_id: string | null        // LLM tool_calls[].id
  params: object
  request_id: string (UUID | null)
  approval_status: string [PENDING | APPROVED | REJECTED | EXPIRED]
  execution_status: string [PENDING_APPROVAL | RUNNING | SUCCEEDED | FAILED]
  error: object | null
  result: object | null
  timestamp: string (RFC 3339)
}
```

`tool_name` 是 `name` 的前端兼容 computed 字段。`executed_tool_list` 可能包含待审批、运行中、成功、失败、拒绝或过期的工具生命周期记录，不只包含已执行完成记录。

### 历史会话 DTO 适配

数据库和会话 REST 接口以 `result` 保存工具执行信封，实时 SSE 使用 `output`。frontend 在基础设施层通过 `SessionDtoAdapter` 完成转换，组件和状态仓库只接触统一的 `ToolCallInfo.output`。

适配规则：

- `result` 是执行信封时，提取 `output`、`error` 和 `execution_time_ms`。
- `result` 是普通 JSON 值时，直接作为 `output`。
- 输出支持字符串、对象、数组、数值、布尔值和 `null`。
- DTO 适配只处理传输格式，不承担界面展示逻辑。

### ToolEvidence 展示模型

工具证据展示由纯函数 `presentToolEvidence(tool_call)` 生成，包含格式化参数、错误和结果预览。结果预览最多 20 行或 16 KiB；完整结果保留在内存中，可由用户复制。

工具卡摘要显示工具名称、R/W 属性、审批状态、执行状态和耗时。展开区域显示 MCP Server、回滚属性、完整参数、结果或错误。这样既保留聊天界面的可读性，也能让评审直接核对诊断依据。

源码：`frontend/vue-project/src/presentation/tool-evidence.ts`

```typescript
export function presentToolEvidence(toolCall: ToolCallInfo): ToolEvidencePresentation {
  return {
    parameters: formatJson(toolCall.params ?? {}),
    ...(toolCall.error ? { error: formatJson(toolCall.error) } : {}),
    ...(toolCall.output !== undefined ? { result: presentResult(toolCall.output) } : {}),
  }
}

function presentResult(output: ToolCallInfo['output']): NonNullable<ToolEvidencePresentation['result']> {
  const fullText = typeof output === 'string' ? output : formatJson(output)
  const lines = fullText.split('\n')
  const lineLimited = lines.slice(0, MAX_RESULT_LINES).join('\n')
  const byteLimited = limitUtf8Bytes(lineLimited, MAX_RESULT_BYTES)

  return {
    fullText,
    previewText: byteLimited.text,
    truncated: lines.length > MAX_RESULT_LINES || byteLimited.truncated,
  }
}
```

### ToolRequest

审批请求是内存态等待对象。它通过 SSE `tool_approval_required` 暴露给前端，通过 REST 审批端点回写决策，不单独持久化为独立表。REST 审批请求必须携带同一 SSE 事件中的 `chat_id`，后端拒绝缺失或与 `request_id` 归属不一致的决策。审批进入批准、拒绝或过期状态时，同一个 `request_id` 会写回对应 `tool_calls` 行。

```
ToolRequest {
  request_id: string (UUID)
  chat_id: string (UUID)
  message_id: string (UUID)
  params: object
  approval_status: string [PENDING | APPROVED | REJECTED | EXPIRED]
  created_at: string (RFC 3339)
  approved_at: string (RFC 3339 | null)
  expired_at: string (RFC 3339 | null)
  rejected_reason: string | null
}
```

## SSE 事件契约

`POST /api/chat` 返回 `text/event-stream`。首事件必须是 `session_init`，末事件必须是 `done`。

| event | data | 说明 |
|-------|------|------|
| `session_init` | `{chat_id}` | 建立流后立即返回真实 UUID |
| `reasoning` | `{delta}` | LLM `reasoning_content` 增量 |
| `thinking_done` | `{}` | 当前推理片段结束 |
| `assistant` | `{delta}` | LLM 正文增量 |
| `assistant_done` | `{}` | assistant 消息边界 |
| `tool_call` | `{call_id, tool_name, params, is_read_only, server}` | 工具开始执行或展示 |
| `tool_result` | `{call_id, execution_status, output?, error?, execution_time_ms?}` | 工具执行结果；SSE/UI 状态为 `SUCCEEDED` / `FAILED` / `REJECTED`，`output` 允许任意 JSON 值 |
| `tool_approval_required` | `{chat_id, request_id, tool_name, params, reason, call_id}` | 高风险工具等待审批 |
| `error` | `{code, message}` | turn 级错误 |
| `done` | `{}` | 流结束；断连或异常路径也会在 finally 中发送 |

`call_id` 使用 LLM `tool_calls[].id`，对应数据库字段 `llm_tool_call_id`，用于 SSE `tool_call` 和 `tool_result` 配对。每个已发送的 `tool_call` 都必须在依赖该结果的 assistant 文本和 `done` 前收到一个匹配 `tool_result`。前端不得依赖 `X-Session-ID` header；session ID 只从 `session_init` 获取。

工具结果的 SSE 序列化保留同一个 `call_id`，并按实际存在的字段输出结果、错误和耗时。

源码节选（省略调试日志）：`web-server/src/sse_stream.py`

```python
def _tool_call_finished_to_wire(self, event: ToolCallFinished) -> WireEvent:
    data: dict = {
        "call_id": event.call_id,
        "execution_status": event.execution_status,
    }
    if event.output is not None:
        data["output"] = event.output
    if event.error is not None:
        data["error"] = event.error
    if event.execution_time_ms is not None:
        data["execution_time_ms"] = event.execution_time_ms
    return {"event": "tool_result", "data": json.dumps(data)}
```

## System Prompt 结构

System prompt 由多个命名 section 按固定顺序组装为单一 prompt 注入 LLM：

`identity → rules → tool_usage → diagnostic_reporting → environment → memory`

| Section | 类别 | 职责 |
|---------|------|------|
| `identity` | 静态 | Agent 角色身份与核心能力描述 |
| `rules` | 静态 | 强制遵守的行为规则 |
| `tool_usage` | 静态 | 工具调用规范、并行策略、错误处理 |
| `diagnostic_reporting` | 静态 | 有证据的故障诊断使用六段式 RCA，普通对话保持简短 |
| `environment` | 动态 | 目标系统静态信息；动态指标通过工具按需获取 |
| `memory` | 动态 | 持久记忆内容 |

当前运行时默认使用 `PromptManager` 内置 section；可通过构造 `PromptManager(prompt_path=...)` 覆盖，但生产启动路径默认不加载 `prompt.md`。

### 结构化 RCA 契约

`diagnostic_reporting` 仅在“已完成故障诊断且已有工具证据”时生效，最终回答使用以下标题：

```
## 根因结论
## 关键证据
## 置信度
## 备选原因
## 影响范围
## 处置建议与风险
```

普通问候、能力介绍和纯操作确认不套用该结构。该约束用于提高诊断报告的一致性，不把无证据回答包装成根因分析。

## 输入安全设计

输入安全规则位于 `web-server/config/rules.json` 的 `input_safety` 数组。每条规则包含 `id`、`patterns` 和 `reason`。当前规则覆盖：

- 改写或忽略系统安全指令。
- 索取 system prompt 或开发者指令。
- 索取凭据、密码、API Key、访问令牌或私钥。
- 绕过审批、权限或安全检查。

评估前先执行 Unicode NFKC 规范化和 `casefold()`。规则按配置顺序匹配，首次命中即返回 `BLOCK`。为了减少否定表达误判，规则对“do not”“never”“不要”“禁止”等常见安全表达设置边界测试。

审计结构：

```json
{
  "actor": "POLICY",
  "event": "INPUT_REJECTED",
  "decision": "BLOCK",
  "error": {
    "rule_id": "bypass_approval_controls",
    "reason": "检测到试图绕过审批或安全控制的提示注入"
  }
}
```

当前实现针对已知高置信模式，不宣称覆盖语义改写、编码混淆和所有未知攻击；正则评估尚无独立超时保护。

`ChatTurn` 在构建 AgentState 之前调用安全门。命中后先审计，再返回错误并结束；`_build_agent_state()` 和后续 LLM 编排不会执行。

源码：`web-server/src/chat_turn.py`

```python
history = await self._persist_user_message(session)
assessment = self._input_safety_gate.assess(self._user_message)
if assessment.decision is SafetyDecision.BLOCK:
    await self._audit_rejection(chat_id_uuid, assessment)
    yield TurnFailed(
        code="PROMPT_INJECTION_BLOCKED",
        message=assessment.reason or "Prompt injection blocked",
    )
    return

state = self._build_agent_state(history)
orchestrator = self._orchestrator_builder()
```

## 操作分级规则

分级来源：

- 静态工具：工具注册元数据 `is_read_only` / `is_rollbackable`
- 可变工具：伴生分类工具 `{tool_name}_classify` 返回 `{"safe": bool}`

规则引擎只按工具名匹配 `rules.json`：

| 判定顺序 | 条件 | 行为 |
|----------|------|------|
| 1 | 工具名在 blacklist | `REJECT`，不执行 |
| 2 | 工具名在 whitelist | `AUTO_APPROVE` |
| 3 | `is_read_only=true` | `AUTO_APPROVE` |
| 4 | 其他 | `REQUIRE_APPROVAL` |

可变工具分类失败时 fail-closed，按 `safe=false` 进入审批路径。

`bash_classify` 的 `safe` 语义只用于“是否可免审批只读执行”：

- `safe=true`：命令是运维观测/读取类命令，可按只读工具处理。
- `safe=false`：命令需要审批；不表示 tool-server 强制禁止。

当前 bash 分类规则先用 `tree-sitter-bash` fail-closed 解析 AST，再拒绝命令替换、进程替换、重定向、子 shell、复杂控制结构、危险换行等 shell 执行面；随后按运维只读 allowlist 校验命令、子命令、flag 和路径。敏感读取（如 `/etc/shadow`、`~/.ssh/*`、`/proc/*/environ`）、网络请求（如 `curl`、`wget`、`ssh`、`nc`）、shell wrapper（如 `bash -c`、`sh -c`、`eval`、`xargs`）、可写 flag（如 `sed -i`、`git diff --output`）均返回 `safe=false`。

## MCP 通信协议

web-server 与 tool-server 通过 fastmcp 调用 MCP `tools/call`。

### 多 MCP Server 发现与云平台接入

架构具备云平台接入能力，可通过新增 MCP Server 扩展云资源查询与运维。web-server 从 `servers.json` 读取服务列表，`ServerRegistry` 逐个完成工具发现，并给每个公开工具附加 `server_name`。工具调用进入审查层后，`ToolExecutor` 使用该字段取得目标 URL，Agent 主循环不需要包含任何云厂商分支。

源码核心结构（省略连接重试与日志分支）：`web-server/src/mcp_client/registry.py`

```python
def __init__(self, servers: list[ServerEntry]) -> None:
    self._servers = {s.name: s for s in servers}
    self._tools: list[dict] = []

async def discover(self) -> list[dict]:
    all_tools: list[dict] = []
    for entry in self._servers.values():
        server_tools = await self._fetch_tools(entry)
        all_tools.extend(server_tools)
    self._tools = all_tools
    return all_tools

def url_for(self, server_name: str) -> str:
    return self._servers[server_name].url
```

新增云平台 MCP Server 的接入步骤保持在基础设施边界内：

1. 将云资源查询与运维 API 封装为 MCP Tool。
2. 为工具声明输入 schema、输出 schema、`mutable`、`is_read_only` 和 `is_rollbackable`。
3. 对参数决定风险的运维工具配套 `{tool_name}_classify`。
4. 在 `servers.json` 增加服务地址，由现有发现、审查、审批、路由和调用流程接管。

查询类工具可以直接复用只读自动审批与并行执行；变更类工具进入现有人工审批流程。这样，云资源能力与本地 OS、PostgreSQL 和 eBPF 工具使用同一套 Agent 交互和证据模型。

```json
  "params": {
    "name": "bash_classify",
    "arguments": { "command": "rm -rf /var/lib/mysql" }
  },
  "id": 1
}
```

伴生工具的文本内容应能解析为：

```json
{ "safe": false }
```

解析失败、调用失败、字段缺失均视为 `safe=false`。

### 工具执行调用

web-server 对 tool-server 的实际执行统一调用隐藏工具 `execute_tool`，由该入口再分发到真实工具名。web-server 在 `execute_tool` 参数中携带以下执行元数据：

```
tool_name
chat_id
params
approval_status
request_id
auth_token
```

当前 `ToolExecutor.execute()` 要求 `approval_status == APPROVED`，否则本地返回安全违规结果，不向 MCP server 发起执行。只读预执行工具也会携带 `approval_status=APPROVED`、生成的 `request_id` 和所属 `chat_id`。web-server 更新工具生命周期时按 `tool_calls.id + chat_id` 定位，并在审批决策落地时持久化 `request_id`。tool-server 使用 `chat_id + tool_name + params` 绑定 `request_id` 的缓存和 in-flight 复用上下文，避免跨会话复用审批或执行结果。`auth_token` 来自 `TOOLSERVER_SHARED_SECRET`；tool-server 配置共享密钥后会对该 token 做常量时间比较。直接调用可变工具（如 `bash`）会被 tool-server 拒绝。

实际执行前，生命周期先查找工具并完成安全校验；只有校验通过后才进入缓存复用和真实调用。安全失败返回结构化结果，不触发工具函数。

源码：`tool-server/src/execution_lifecycle.py`

```python
tool = await _lookup_tool(server, tool_name, chat_id)
if isinstance(tool, dict):
    return tool

is_read_only = (tool.meta or {}).get("is_read_only", False)
security_error = _validate_tool_request(
    approval_status,
    request_id,
    is_read_only,
    auth_token,
    shared_secret,
    tool_name,
    chat_id,
)
if security_error is not None:
    return security_error

context = _cache_context(chat_id, tool_name, params)
reusable, inflight = await _reusable_result_or_inflight(
    cache, request_id, context, tool_name, chat_id
)
```

成功结果规范：

```json
{
  "execution_status": "SUCCEEDED",
  "output": "..."
}
```

失败结果规范：

```json
{
  "execution_status": "FAILED",
  "error": { "message": "..." }
}
```

## 审查与执行流程

1. web-server 持久化用户消息后调用 `InputSafetyGate`；命中时终止本轮。
2. 通过输入检查后构建 AgentState 并调用 LLM。
3. LLM 返回 tool_calls 后，web-server 解析 `server__tool` 前缀并补齐工具元数据。
4. 静态只读工具直接并行预执行，生成 `streaming_tool_results`。
5. 静态写工具和可变工具进入审查层。
6. 可变工具调用伴生分类工具；分类失败按危险处理。
7. `RuleEngine.evaluate()` 按 blacklist、whitelist、只读、默认审批的顺序决策。
8. 自动批准工具进入 `act_node` 并行执行。
9. 高风险工具通过 SSE `tool_approval_required` 等待用户审批。
10. 用户审批通过后执行；拒绝或超时则生成 LLM 可见的 tool-result 拒绝消息。

默认审批等待超时为 300 秒。测试可通过 mock 或依赖注入缩短等待，不依赖生产配置文件自动切换。
审批 REST 请求只接受 `APPROVED` / `REJECTED`。`PENDING` 是服务端等待态；`EXPIRED` 只由服务端超时或缺失审批 bridge 时内部生成。

### ToolRequest / ToolCall 状态机

```mermaid
stateDiagram-v2
    [*] --> DISCOVERED: LLM tool_call
    DISCOVERED --> PRE_EXECUTED: static readonly
    PRE_EXECUTED --> SUCCEEDED
    PRE_EXECUTED --> FAILED

    DISCOVERED --> REVIEW: static write or mutable
    REVIEW --> REJECTED: blacklist
    REVIEW --> APPROVED: whitelist or readonly classification
    REVIEW --> PENDING: requires approval

    PENDING --> APPROVED: user approves
    PENDING --> REJECTED: user rejects
    PENDING --> EXPIRED: timeout

    APPROVED --> RUNNING: execute
    RUNNING --> SUCCEEDED
    RUNNING --> FAILED

    REJECTED --> [*]: tool message tells LLM do not retry
    EXPIRED --> [*]: tool message tells LLM approval expired
    SUCCEEDED --> [*]: result back to LLM
    FAILED --> [*]: error back to LLM
```

`SECURITY_VIOLATION` 是工具执行返回中的错误语义，不是数据库 `execution_status` 枚举值；持久化时映射为 `FAILED` 并携带 error。

用户拒绝或审批过期同样在数据库中持久化为 `execution_status=FAILED`，同时保留 `approval_status=REJECTED|EXPIRED`。对 SSE、前端和 LLM history，web-server 会发出匹配原 `call_id` 的 `tool_result`，其中 `execution_status=REJECTED`，用于关闭前端工具条并让 LLM 继续推理。

## 错误处理

### MCP 调用层

| 场景 | 策略 |
|------|------|
| 连接错误 | 最多重试 2 次，间隔 1s / 2s；仍失败则返回 `FAILED` |
| 调用超时或运行时错误 | 不重试，返回 `FAILED` |
| 伴生分类失败 | fail-closed，视为 `safe=false` |
| `approval_status != APPROVED` | 本地返回 `SECURITY_VIOLATION` 语义错误 |

业务级重试由 Agent/LLM 决定；MCP 客户端只做传输层最小重试。

### Agent 熔断

| 熔断 | 默认值 | 行为 |
|------|--------|------|
| 最大迭代轮次 | 30 | 触发 `TURN_LIMIT_EXCEEDED` SSE error 并退出 |
| Token 硬上限 | context window × 0.95 | 压缩后仍超限时触发 `TOKEN_BUDGET_EXCEEDED` |

当前不实现“轮次到达后等待用户确认继续”的交互式暂停。

### 服务崩溃恢复

当前代码不实现启动扫描 `RUNNING` tool_calls 并重放执行，也不实现后台兜底任务。若 web-server 在工具执行后、结果写回前崩溃，可能留下 `RUNNING` 记录，需要人工根据 `audit_events`、`tool_calls` 和宿主状态排查。

### LLM 错误分类与恢复

LLM Adapter 将错误映射为标准分类：

| 分类标签 | 触发条件 | 当前恢复策略 |
|----------|----------|--------------|
| `prompt_too_long` | 400/413 且上下文过长相关 | 压缩上下文；仍失败则激进压缩 |
| `max_output_tokens` | stop_reason=max_tokens | 提升 max_tokens；仍失败则最多 3 次注入 continue |
| `model_unavailable` | 404 | 若配置 fallback model，则切换 |
| `server_error` | 5xx / 529 | 若配置 fallback model，则切换 |
| `rate_limit` | 429 | 不恢复，表面错误 |
| `auth_failed` | 401 / 403 | 不恢复，表面错误 |
| `timeout` | status_code=0 | 不恢复，表面错误 |
| `unknown` | 其他 4xx/异常 | 不恢复，表面错误 |

`llm_traces` 当前记录 prompt、completion、token 和 latency；不包含独立的 `error_type` / `error_details` 列。

## 可观测性

| 系统 | 存储 | 内容 | 详见 |
|------|------|------|------|
| 审计日志 | PostgreSQL `audit_events` | 审查决策、审批、执行结果、transition、错误事件 | `docs/数据库设计.md` |
| LLM 追踪 | PostgreSQL `llm_traces` | 每次 LLM 调用的 prompt、completion、token、延迟 | `docs/数据库设计.md` |
